## Перенос остатка бенефициара — 12 ноября 2026

Business Registry синхронизирован с локальным `openapi.yaml` и `docs/admin-beneficiary-migration-handoff.md` backend: 12 endpoint и их связанные схемы. Фильтр банка допускает множественный выбор: фронтенд объединяет выбранные статусы по OR, передавая скалярный `bank_status` в каждой ветке запросов. Все сочетания юридического типа и статуса сохраняют отдельные offsets; выбор всех банковских статусов не создаёт лишних веток. Карточка показывает целые рубли `available_rub`/`blocked_rub` и необязательный `balance_transfer_status`.

Смена типа/ИНН использует прежний PATCH partner и полный новый ключ ответа. По последнему требованию владельца суммы available_rub и blocked_rub не ограничивают форму; предупреждение об ожидании зарезервированных средств убрано, серверное правило обновляется на бэкенде. VERIFIED подтверждает завершение смены только без переноса или вместе с DONE. Активные фазы переноса опрашиваются, REVIEW_REQUIRED требует ручной сверки и не предлагает повторный перевод. UI не обращается к Точке и не меняет внутренний баланс самостоятельно.

Проверено на подменённом API в браузере: ИП→ООО с положительным доступным остатком, нулевой/положительный резерв, новый id и адрес карточки, ожидание документов, все активные фазы, DONE и REVIEW_REQUIRED, отсутствующие поля старого backend, мобильный вид и выбор/замена/очистка bank_status. Реальный банковский перевод этими проверками не выполняется.

Read-only HTTP-проверка работающего `localhost:8080` для BUSINESS/REFERRAL, с фильтром VERIFIED и без него, получила 401. Наличие новых полей в действующем API и реальный банковский перенос не подтверждены; сервер не перезапускался. Фронтенд: 47/47 тестов, build и lint без ошибок (с прежними предупреждениями).

## Выполненные исправления

- Убраны фиксированные имя администратора, роли сотрудников, фото мастера,
  выдуманные причины отмены и сообщения о распределении оплаты.
- Профиль администратора определяется через собственные права и API сотрудников.
  Без права ROLES показывается действительный ID аккаунта, без выдуманного имени.
- CAPTCHA и временный токен удалены по указанию владельца проекта, включая
  повторную отправку OTP. Запрос без заголовка CAPTCHA с пустым телом получает
  `400 Phone cannot be empty`, то есть доходит до валидации номера без отправки SMS.
- Восстановление сессии сохраняет тело PATCH/POST до первого fetch и повторяет
  запрос с обновлённым JWT; ошибки поддерживают оба поля error_code/codeError.
- Модерация, записи и обращения используют реальные файлы. Документы, аудио,
  голосовые и видео открываются по ID через API файлов; отправка сообщения ждёт
  обработки UPLOADED. Некорректные числовые ID файлов отклоняются.
- Категории профиля берутся из доступных категорий конкретного мастера/салона,
  без требования лишнего доступа к общему разделу категорий.
- Документы: частичные PATCH только изменённых полей, без пустого comment;
  редактирование паспортных данных, загрузка дополнительных документов,
  статусы банка и повторная проверка. Ответы обновляют полный ключ заявки;
  завершение операции не открывает уже закрытую или другую заявку.
- Рассылки сохраняют существующие триггеры и условия при редактировании;
  проверяются целая положительная задержка и будущее время отправки.
  Убран фильтр периода, которого нет в API уведомлений.
- Основные серверные списки, приглашённые партнёра и комментарии заявки
  используют бесконечную прокрутку: offset, has_more/total, защита от дублей,
  сброс при изменении фильтров, сохранение строк и повтор при ошибке догрузки.
  Внутренняя история сообщений обращения пока загружается прежним способом.
- Права DOCUMENTS и COMPLAINTS учитываются в меню и маршрутах.

## Что требуется от бэкенда

1. **График лояльности:** `GET /api/admin/referral/profit?from=2026-11-01&to=2026-11-11`
   возвращает `500`, `internal_error`. На странице показана ошибка с повтором,
   демонстрационная линия не подставляется.
2. **Собственный профиль ADMIN без доступа ROLES:** `GET /api/user` возвращает
   `403` из-за требования USER authority. Нужен собственный endpoint профиля
   администратора, доступный независимо от просмотра остальных сотрудников,
   либо разрешение ADMIN на чтение своего `/api/user`.
3. **Смена юрстатуса:** PATCH существует, но требует документы, загруженные
   владельцем, и сведения об обязательных документах нового типа. Карточка
   админки не даёт полного набора типов/владения для выбора этих файлов.
   Нужны метаданные доступных документов и требований перехода или разрешённая
   административная загрузка документов для перехода. Пока выбор статуса
   отключён с объяснением; неполный PATCH больше не отправляется.
4. **Доставка уведомлений:** текущий контракт сохраняет правила и расписание,
   но MVP не выполняет доставку. Создание правила в интерфейсе не подтверждает
   фактическую отправку получателям.
5. **Должности сотрудников и единицы сумм:** отдельного поля должности нет;
   единицы spent_amount/income_amount в контракте не определены. UI показывает
   денежные значения как рубли; единицы следует явно описать в спецификации.

### Обновления поддержки через WebSocket

Локальный backend разрешает WS Origin `http://localhost:8080`, но отклоняет
`http://127.0.0.1:5173` с HTTP 403. Для локального Vite-прокси `/ws` включён
`rewriteWsOrigin`: запрос браузера через порт 5173 теперь получает HTTP 101.
Подтверждено авторизованное STOMP CONNECTED с действующим admin ID.
После подписок и при переподключении инвалидируется кэш `support-chats`,
чтобы обновить список, карточку обращения и сообщения после пропущенных событий.
Тест `support-realtime.test.mjs` проверяет очереди сообщений/статуса/прочтения
и повторное обновление после обрыва. Сообщения в реальные обращения при проверке
не отправлялись; backend не менялся и не перезапускался.

### Переписка из жалобы

В жалобах на пользователя, мастера и салон кнопка «Перейти в чат» открывает
модальное окно конкретного диалога из `ComplaintDetails.dialog_id`.
При отсутствии этого поля вместо кнопки показывается текст «Диалога между этими
пользователями нет». Окно чата не открывается, остальные диалоги не запрашиваются.
История берётся из `/api/admin/clients/chats/{dialogId}/messages`, предыдущие
сообщения загружаются по `beforeId` (либо offset для ответа без курсора).
Реальный GET жалобы №547 вернул 200 без `dialog_id`; для показа её переписки
backend должен найти приватный диалог участников и вернуть этот идентификатор.

### Множественные фильтры при одиночных параметрах API

API списка партнёров принимает по одному `client_level_code`, `business_level_code`
и `status`; API документов — один `business_type` и один `bank_status`. Фронтенд объединяет ответы
для всех выбранных комбинаций (OR внутри одного фильтра, AND между фильтрами).
Для каждого запроса сохраняется отдельный offset; завершённые ветки больше
не запрашиваются. Счётчики суммируются, строки дедуплицируются по идентификатору
партнёра либо составному ключу документа. Ошибка одной ветки не выдаётся за полный
результат. Очистка всех чекбоксов делает один запрос без соответствующих фильтров.
Другие API с нативными массивами продолжают получать массивы напрямую.

### Загрузка защищённых документов

Просмотр использует новый `/api/file/download/{id}?type=FULL&inline=true&redirect=false`
с JWT. Незашифрованный файл отдаётся как JSON с подписанной inline-ссылкой;
зашифрованный — бинарным ответом (также для фото). Первый отображается напрямую,
второй через blob URL с очисткой при закрытии. При 401 применяется single-flight
refresh. JWT не добавляется в URL и не отправляется на сторонний storage.
Проверка 1071: новый endpoint=200, сам PDF=200/application/pdf, 86298 байт,
`Content-Disposition: inline`; обычное скачивание сохраняет `attachment`.
Отсутствие CORS у storage не мешает навигации iframe/img. Исторический
`docs/patches/backend-pdf-inline.patch` больше не нужен: backend реализовал
параметр inline. Сервер агентом не перезапускался.
Проверка 11.11.2026: `GET localhost:8080/api/file/download/9937788372711?type=FULL`
с JWT администратора возвращает 500 `File download failed`. Это отдельный сбой
серверной выдачи/расшифровки файла, после прохождения авторизации.

### Подсказки городов, адресов и передача гео

В редактировании салона связка переведена на `/api/search/places` (limit=5),
затем `/api/search/addresses` (limit=10) с `fias_id` и `type` выбранного города
или посёлка. Название, FIAS и тип хранятся в состоянии формы; в PATCH салона
вместе отправляются `city`, `address` и `geolocation`. При изменении города
адрес/гео очищаются, адрес заблокирован до выбора города из подсказки.
Задержка ввода — 300 мс. Имеющийся адрес не мешает сохранению других полей.
Браузерная проверка 390/1440 px покрывает city/settlement и точный PATCH
с перехватом записи (реальные данные не менялись). Реальная проверка 11.11.2026:
`GET localhost:8080/api/search/places?query=Москва&limit=5` с JWT повторно
возвращает 500 `Internal server error`; подсказки зависят от исправления backend.

В профиле мастера для `CLIENT_PLACE` доступен максимальный радиус выезда:
1, 5, 10 или 20 км (варианты контракта API). Значение сохраняется в `radius_km`
соответствующей локации. В админке выбор радиуса обязателен при включённом
«У клиента»: сохранение заблокировано, пока не выбраны 1, 5, 10 или 20 км.
Адрес самого мастера редактируется в `AT_MASTER_PLACE` с координатами из подсказки.

Отдельного базового адреса/гео мастера для выезда в административном GET/PATCH
профиля нет. Для независимого редактирования точки отправления нужны отдельные
поля `address`/`geolocation` в API. `CLIENT_PLACE` не принимает адрес/гео, а включать
`AT_MASTER_PLACE` только ради точки отправления некорректно: это включает приём у мастера.

Смена только `city` у мастера: форма отправляет изменённый город без неизменённых
`service_locations`. В backend `MasterService.prepareServiceLocations` при отсутствии
списка сразу возвращается, затем `UserService.resolveUserLocation` вызывает DaData
для нового города без координат. Ошибка этого вызова выдаётся как
`Failed to geocode user location` (наблюдалась в админке при смене города).
Внешнюю причину сбоя DaData нужно уточнять по серверному логу; административный
контракт мастера не принимает корневую `geolocation` для обхода этого вызова.

У клиента и мастера города запрашиваются через `/api/suggestions/cities`,
адреса — через `/api/suggestions/address`. Выбранный адрес и его числовые `lat/lon`
передаются вместе: у клиента/салона в `address` + `geolocation`, у мастера — внутри
соответствующей записи `service_locations`. Ручной ввод сбрасывает ранее выбранные
координаты; адрес без выбора подсказки не отправляется. Неизменённые локации мастера
сохраняют свои координаты, у `CLIENT_PLACE` фиксированный адрес/гео не передаются.

Проверка localhost:8080: адресные подсказки возвращают 200 с реальными координатами;
`/api/suggestions/cities?query=Санкт&limit=20` возвращает 422 с сообщением
`Failed to get place suggestions`. Ошибка города отображается в форме. Проверка
сохранения форм выполнена в изолированном браузере с перехватом PATCH — данные
реальных профилей не изменялись. Проверены обе локации мастера, клиент, салон,
сброс устаревшего гео, сохранение координат остальных локаций, выбор клавиатурой.
