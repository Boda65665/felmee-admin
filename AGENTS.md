## Процесс переноса из Figma

Главный принцип: **плоско, а не преждевременно разбито.** Экран сначала
пишем чистым, но цельным; в общее выносим только доказанное переиспользование,
а не предполагаемое (YAGNI + правило трёх — абстракция на 3-м повторе, не на 1-м).
Неправильную абстракцию убирать дороже, чем дублирование.

Порядок работы с каждым импортом:

1. **Импорт из Figma.** `get_design_context` (+ скриншот, `get_variable_defs`).
   Ассеты скачиваем в `src/assets/` (точные байты, не временные URL). Новые
   цвета/шрифты — в токены `src/index.css`, не хардкодим по месту. `node-id`
   экрана заносим в реестр `docs/screens.md`; скриншоты — в кеш `.figma/`
   (в `.gitignore`), в репо не коммитим (устаревают, источник правды — Figma).
2. **Чистый плоский код экрана.** Сразу читаемо: без магических дублей;
   самодостаточную логику (маска, валидация) выносим в функции, но экран пока
   остаётся одним файлом в `src/pages/`.
3. **Выносим только очевидные атомы дизайн-системы** — `Button`, `Input` и т.п.
   Они повторяются на каждом экране, риск нулевой. Варианты — через `props`/CVA
   (OCP), а не копипастом. Каждый компонент — одна ответственность (SRP).
4. **Композиты (layout, панели, секции) НЕ выделяем**, пока второй экран не
   докажет паттерн. Появился повтор — тогда выносим, имея 2+ примера перед глазами.
5. **Рефакторинг:** Запустите /simplify перед представлением кода пользователю.
6. **Проверка:** `pnpm build` + `pnpm lint` (+ визуальная сверка со скриншотом).

Документацию ведём **одну живую на дизайн-систему** (`docs/design-system.md`:
токены, примитивы, их варианты), а не отдельный файл на каждый экран — иначе
дублирует Figma и устаревает. По экрану достаточно строки в «Статусе работ» в `CLAUDE.md`.
